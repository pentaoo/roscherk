# Как в проекте Sheji использовалась нейросеть

Этот файл описывает, как в проекте **Sheji** применялась нейросеть: для проектирования интерфейса, переноса Figma-идей в код, архитектурной декомпозиции, генерации контента, документирования решений и проверки качества.

Sheji - статический сайт модного e-commerce бренда: HTML, CSS и vanilla JavaScript без сборщика и фреймворков. При этом проект развился в полноценную витрину с коллекциями, каталогом, фильтрами, поиском, карточками товара, корзиной, избранным, страницами показов, локализацией EN/RU и экспериментальными мини-играми внутри карточек коллекций.

## Источники, которые использовались как контекст для AI

В проекте был создан отдельный слой документации `ai-context/`. Он нужен, чтобы нейросеть не работала вслепую и не каждый раз заново угадывала стиль, стек и ограничения.

Основные файлы контекста:

- `ai-context/00-operating-rules.md` - правила работы AI перед изменениями.
- `ai-context/project/overview.md` - краткое описание проекта и ограничений.
- `ai-context/project/AGENTS_Sheji.md` - подробная продуктовая и визуальная спецификация Sheji.
- `ai-context/design/figma-notes.md` - заметки по Figma-фреймам, размерам и визуальным решениям.
- `ai-context/design/tokens.md` - стабильные цвета, motion-токены и правила анимации.
- `ai-context/code/file-map.md` - карта файлов и JS-модулей.
- `ai-context/code/conventions.md` - кодовые соглашения.
- `ai-context/decisions/decision-log.md` - журнал устойчивых решений.
- `ai-context/tasks/collection-mini-games.execPlan.md` - подробный план реализации скрытых мини-игр.
- `ai-context/qa/checklist.md` - чеклист проверки перед завершением задач.
- `docs/sitemap.md` и `docs/sitemap-visual.svg` - карта сайта, пользовательские потоки и известные ограничения.

Отдельные экспортированные диалоги с нейросетью в репозитории не найдены. Соседний файл `../chat`, который выглядел как возможный источник диалогов, содержит только короткую строку `fdagfd`, поэтому в этом README использованы реальные артефакты проекта: AI-контекст, Git-история, структура файлов и текущая реализация.

## Для чего применялась нейросеть

### 1. Формирование концепции продукта

AI помогал удерживать целостную концепцию Sheji:

- не нейтральный fashion-магазин;
- не шаблонный Shopify-style storefront;
- яркая, странная, громкая, коммерческая и немного провокационная платформа;
- визуальная энергия ближе к MSCHF, чем к минималистичному luxury;
- магазин должен оставаться функциональным, но интерфейс может вести себя как арт-объект.

Эта идея закреплена в `ai-context/project/AGENTS_Sheji.md`. Там же явно указано, что проект называется Sheji, а не NOSOK, и что нельзя переносить старые брендовые допущения из других проектов.

### 2. Перевод Figma-идей в HTML/CSS/JS

Нейросеть использовалась как помощник для переноса дизайнерских решений из Figma в статический сайт.

В `ai-context/design/figma-notes.md` зафиксированы, например, заметки по hero refresh:

- Figma-фреймы `4700:7695` и `4700:7093`;
- белый холст;
- желтые карточки коллекций слева;
- активная карточка `STONE` около `734x402`;
- соседние карточки со scale/rotation;
- зеленый квадрат CTA;
- product collage справа;
- expanded collection hero с желтой левой панелью около `626px`;
- сохранение language switcher вне Figma-фреймов по продуктовому решению.

AI применялся не только для верстки "по картинке", но и для перевода макета в устойчивые UI-паттерны: карточки, состояния, переходы, data-driven рендеринг, адаптивные ограничения.

### 3. Создание проектной памяти для будущих AI-сессий

Один из важных приемов - не держать знания только в чате, а сохранять их в репозитории.

Так появился каталог `ai-context/`, который работает как локальная память для AI-ассистентов. В нем фиксируются:

- продуктовые правила;
- визуальная система;
- архитектура файлов;
- принятые решения;
- pending-задачи;
- QA-чеклист;
- ограничения на анимации;
- правила использования локальных SVG-иконок.

Это снижает риск, что нейросеть в следующей сессии:

- сменит стек на React/Next без причины;
- добавит лишние зависимости;
- сломает существующий стиль;
- забудет про Figma-источник;
- заменит Sheji на чужой брендовый язык;
- начнет хаотично менять анимации.

### 4. Архитектурная декомпозиция vanilla JS

Хотя проект без сборщика, AI помог разложить логику на модули:

- `js/motion.js` - чтение CSS motion-токенов в JavaScript.
- `js/merchandising.js` - нормализация товаров и коллекций.
- `js/runtime.js` - общий runtime и события коллекций.
- `js/collections.js` - карточки коллекций, carousel, expanded state.
- `js/collage.js` - collage/featured look.
- `js/catalogue.js` - каталог, фильтры, избранное, cart interactions.
- `js/product-detail.js` - карточка товара.
- `js/cart.js` - корзина.
- `js/favorites.js` - избранное.
- `js/search-menu.js` - поиск.
- `js/shows.js` - страницы и меню показов.
- `js/i18n.js` - локализация.
- `js/collection-games.js` и `js/collection-game-modules.js` - скрытые мини-игры коллекций.

Важный технический прием: вместо внедрения фреймворка была сохранена статическая структура, но добавлен небольшой runtime-слой.

Например, `ShejiRuntime` отправляет события:

- `sheji:collectionchange`;
- `sheji:collectionnavigate`;
- `sheji:collectionselect`.

Так разные части сайта могут реагировать на выбор коллекции без жесткой связки между модулями.

### 5. Нормализация данных вместо ручного дублирования

AI помог перейти от ручного связывания UI и данных к нормализованной модели:

- коллекции получают стабильные `id`;
- продукты связываются с коллекциями через `collectionId`;
- создается `searchableText` для поиска;
- формируются `Map` для быстрых lookup-операций;
- каталог, карточки товара, показы и рекомендации используют общие данные.

Это реализовано в `js/merchandising.js` через `ShejiMerchandising`.

Прием интересен тем, что для статического сайта не потребовалась база данных или сборщик: данные остаются в `data/*.js`, но поверх них есть легкий слой нормализации.

### 6. Разработка интерактивного e-commerce без backend

С помощью AI были спроектированы и реализованы клиентские состояния:

- корзина;
- избранное;
- выбранный язык;
- фильтры каталога;
- поиск;
- счетчик корзины;
- переходы между товаром, шоу и каталогом.

Persistent-состояния хранятся в `localStorage`:

- `sheji-cart`;
- `sheji-favorites`;
- `sheji-language`.

Проект остается статическим и может работать на GitHub Pages, но при этом дает пользователю ощущение полноценного магазина.

### 7. Локализация EN/RU

AI помог добавить i18n-слой без внешней библиотеки.

В HTML используются атрибуты:

- `data-i18n`;
- `data-i18n-aria-label`;
- `data-i18n-placeholder`;

Модуль `js/i18n.js` применяет переводы к тексту, `aria-label`, `placeholder`, `alt`, `title`. Это особенно важно, потому что проект содержит не только видимый текст, но и интерактивные элементы, где доступность зависит от корректных aria-атрибутов.

### 8. Скрытые мини-игры как продуктовый прием

Один из самых интересных AI-артефактов - план `ai-context/tasks/collection-mini-games.execPlan.md`.

Идея: внутри expanded collection card есть "designer face". Если пользователь быстро нажмет на него 5 раз, откроется мини-игра коллекции.

Для первых 5 коллекций предусмотрены игры:

- Fruity - `Label Bird`;
- Stone - `Erosion Pong`;
- Water - `Drip Runner`;
- Bloom - `Petal Tennis`;
- Chrome - `Mirror Lane`.

AI помог описать это не просто как фичу, а как управляемую state machine:

- `locked`;
- `arming`;
- `opening`;
- `active`;
- `paused`;
- `closing`;
- `ended`.

Также были заранее зафиксированы требования:

- не разрушать expanded card;
- не терять состояние товаров и скролла;
- поддерживать клавиатуру;
- учитывать reduced motion;
- убирать listeners/timers после выхода;
- держать активной только одну игру;
- возвращать фокус на designer face после закрытия;
- не превращать мини-игры в checkout-гиммик или скидочную механику.

Это хороший пример того, как AI использовался для продумывания UX, архитектуры, accessibility и cleanup еще до кода.

### 9. Motion-токены и дисциплина анимаций

В проекте отдельно зафиксировано правило: не менять выразительные анимации без явного согласования.

AI помог сформулировать устойчивый подход к анимациям:

- хранить длительности в CSS custom properties;
- читать их в JS через `ShejiMotion`;
- учитывать `prefers-reduced-motion`;
- анимировать один стабильный outer shell;
- раскрывать внутренний контент внутри него;
- не собирать open/close из нескольких независимых блоков;
- добавлять fallback cleanup, если `transitionend` не сработал.

Это применяется, например, к search panel и collection card transitions.

Интересный прием: "одна стабильная оболочка" для анимации. Вместо замены DOM-узлов или независимого движения нескольких sibling-элементов меняется геометрия одного владельца состояния. Это делает анимации обратимыми и менее ломкими.

### 10. Работа с локальными SVG-иконками

AI помог оформить правила для `source/icons/`.

В проекте локально хранится большой набор Material SVG-иконок. Их имена должны совпадать с Figma/Material naming, чтобы дизайн и код говорили на одном языке.

Правила:

- не переименовывать иконки без причины;
- декоративным иконкам ставить `alt=""`;
- если кнопка только с иконкой, давать `aria-label`;
- если цвет должен управляться CSS, использовать inline SVG или `currentColor`.

Это зафиксировано в `ai-context/assets/icons.md`.

### 11. Генерация и поддержка sitemap-документации

В `docs/sitemap.md` описана структура сайта:

- главная и каталог;
- коллекции;
- мини-игры;
- страницы шоу;
- карточки товаров;
- корзина;
- избранное.

Также там зафиксированы пользовательские переходы, реализованная динамика и потенциальные ограничения:

- только первые 5 коллекций доступны в hero carousel;
- только первые 5 коллекций имеют mini-game configs;
- нет полноценного checkout после cart total;
- размер товара визуально выбирается, но не сохраняется в корзину как отдельная SKU-строка;
- поиск не создает URL-query.

Такой sitemap полезен и для человека, и для будущей нейросети: он показывает не только "что есть", но и "что пока не доделано".

### 12. Документирование решений через decision log

В `ai-context/decisions/decision-log.md` сохранялись устойчивые решения:

- создать `ai-context/` как Markdown knowledge base;
- держать AI-контекст отдельно от `source/`;
- документировать локальное использование SVG-иконок;
- добавить `ShejiMerchandising`;
- добавить `ShejiRuntime`;
- держать commerce-логику каталога за `ShejiCatalogue.createCatalogueCommerce()`.

Это помогает нейросети не спорить с уже принятыми решениями и не возвращаться к старым вариантам.

## Какие техники AI были особенно полезны

### Контекстная папка вместо бесконечного промпта

Вместо того чтобы каждый раз писать длинный промпт, правила вынесены в `ai-context/`. Это делает работу воспроизводимой: следующий AI-ассистент может перечитать проектные правила и продолжить в том же направлении.

### ExecPlan перед сложной фичей

Для мини-игр был создан подробный execution plan: цели, non-goals, state machine, accessibility, performance, cleanup, analytics hooks, visual system и этапы реализации.

Такой подход особенно полезен, когда фича может легко сломать существующий UX.

### "Non-goals" как защита от расползания задачи

В плане мини-игр явно записано, чего не делать:

- не создавать новые routes;
- не редизайнить collection cards;
- не переписывать expansion system;
- не добавлять скидки и аккаунты;
- не менять expressive animation без отдельного согласования.

Это помогает AI не превращать одну задачу в широкий рефакторинг.

### Stable shell для анимаций

Правило "анимировать одну стабильную оболочку" снижает количество визуальных багов, особенно в open/close UI.

Применение:

- search panel;
- collection card expansion;
- reversible transitions;
- cleanup при пропущенном `transitionend`.

### Data-driven UI без сборщика

AI помог использовать данные из `data/*.js` как простой источник правды, не добавляя backend или build step. Это компромисс между "просто статический сайт" и "поддерживаемая структура данных".

### Event seam между модулями

`ShejiRuntime` стал тонким слоем событий между коллекциями, каталогом, collage и другими модулями. Это уменьшает прямые зависимости в vanilla JS.

### AI-readable documentation

Файлы вроде `file-map.md`, `conventions.md`, `tokens.md` и `qa/checklist.md` написаны коротко и фактически. Они удобны не только человеку, но и AI: модель быстрее находит нужные ограничения и меньше галлюцинирует.

### Accessibility как часть промпта, а не финальная заплатка

В AI-контексте и планах заранее указаны:

- `aria-label` для icon-only controls;
- `alt=""` для декоративных иконок;
- keyboard reachability;
- focus return;
- Escape behavior;
- reduced motion;
- inert/aria-hidden для скрытого контента.

Это лучше, чем просить "потом поправить доступность".

## Где AI помогал в текущей реализации

По структуре проекта и истории коммитов видно, что AI применялся в таких направлениях:

- обновление визуала и навигации сайта;
- добавление GitHub Pages support для корзины;
- создание cart page и cart logic;
- добавление product detail pages;
- создание shows pages и event data;
- локализация интерфейса;
- перенос Figma hero refresh;
- обновление collection media slider;
- настройка мобильных состояний каталога, корзины и product panel;
- создание sitemap-документации;
- проектирование и реализация скрытых collection mini-games;
- поддержка AI-контекста и decision log.

## Ограничения использования AI

Нейросеть не использовалась как единственный источник истины. Для проекта важны ограничения:

- стек остается HTML/CSS/vanilla JS;
- внешние зависимости не добавляются без необходимости;
- Figma-заметки и дизайн-токены важнее случайных предложений модели;
- expressive animations требуют согласования;
- пользовательские изменения нельзя перетирать;
- перед завершением задачи нужно проверять layout, accessibility и runtime errors.

Также важно: поскольку экспортированные диалоги не сохранились в репозитории, этот README не цитирует конкретные фразы из чатов. Вместо этого он описывает подтверждаемые следы работы AI в файлах проекта.

## Итог

В этом проекте нейросеть использовалась не только для генерации кода. Она выполняла роль:

- продуктового ассистента;
- дизайн-to-code помощника;
- архитектора vanilla JS структуры;
- автора проектной документации;
- помощника по UX и accessibility;
- ревьюера ограничений;
- инструмента для планирования сложных интерактивных фич.

Главный результат - проект получил не просто набор HTML/CSS/JS файлов, а поддерживаемую систему: с контекстом для будущих AI-сессий, зафиксированными решениями, картой файлов, визуальными правилами, токенами, QA-чеклистом и понятными границами развития.
